## Decision

- This repo now tags releases with git tags, starting from `0.1.0` at the
  commit this decision was captured on — the first tag this repo has ever
  had.
- This tag sequence is **independent of `plugins/kms/.claude-plugin/plugin.json`'s
  own `version` field** (currently `0.10.0`, kept in lockstep across
  manifests by `docs/guardrails/plugin-manifest-version-sync.md`). The two
  numbers track different things: the plugin manifest version is what a
  Claude Code/Codex/Kilo user sees when installing or updating the `kms`
  plugin specifically; the git tag marks a point in this repo's own
  history, which today ships exactly one plugin but isn't structurally
  limited to that.
- No enforced cadence or automation: a tag is added by whoever ships a
  change worth marking, matching `docs/decisions/0005-changelog-generation-design.md`'s
  own "no auto-versioning, no release automation" scope for the
  `changelog` skill this most directly benefits.

## Why

`docs/decisions/0005-changelog-generation-design.md` already designed the
`changelog` skill to generate its range from "commits since the last git
tag," with a full-history fallback explicitly because no tags existed at
the time. That fallback has been the *only* path ever exercised — every
one of this repo's changelog entries so far (`0.5.0` through `0.10.0`)
was generated by rescanning the entire commit history, not just what's
new since the previous version. Tagging now makes the intended, cheaper
path actually run, and gives a stable reference point (`git checkout
0.1.0`, a precise diff between releases, something a GitHub Release could
point at) that plugin.json's version field alone doesn't provide.

Starting fresh at `0.1.0` rather than jumping to `0.10.0` (to match
`plugin.json`) keeps the two numbers honestly separate from the start —
matching them would imply a coupling ("the repo's Nth tag = the plugin's
Nth version") that doesn't hold once this repo ships anything beyond the
one current plugin, or bumps the plugin's version without a
tag-worthy repo-level moment (or vice versa).

## Tradeoffs considered

- **Tag to match `plugin.json`'s current `0.10.0`**: keeps one number
  instead of two, simpler to explain today. Rejected — conflates a
  per-plugin manifest version with a repo-level release marker, which
  stops being simple the moment a second plugin or a repo-level change
  outside `plugins/kms/` needs its own release marker.
- **Backfill tags for every prior `plugin.json` version bump
  (`0.5.0`–`0.10.0`)**: gives the `changelog` skill a working "since last
  tag" range for historical entries too. Deferred, not rejected — nothing
  about starting fresh at `0.1.0` precludes doing this later; it just
  wasn't required to unblock the fallback going forward.
- **No tags, keep the full-history fallback indefinitely**: zero process
  overhead, but the fallback was always meant to be temporary
  (`docs/decisions/0005-...`'s own framing), and it silently gets more
  expensive to reason about ("what's actually new since 0.10.0?") as
  history grows.
- **Chosen**: tag from `0.1.0` going forward, kept explicitly independent
  of `plugin.json`'s version.
