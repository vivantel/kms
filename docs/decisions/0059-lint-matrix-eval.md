## Decision

`evals/lint-matrix/` holds a clean project and 24 projects, each with exactly one seeded violation of one lint check, generated by `build.py` (fixtures and `labels.json` are committed and a unit test fails if they drift from the generator). The model answers with one line, `LINT_FINDINGS: <check numbers or NONE>`. `score.py` reports, per check, precision, recall and run-to-run variance over repeated runs (`--repeat 5`), splits structural checks (run by `lint_check.py`, decision 0058) from judgment checks, and reports the clean control's false-alarm rate. A label is the target check plus any check the deterministic checker also reports on that fixture (an audit-log fact is also an orphan). The runner takes `vars.fixture_dir` per test so one config runs all cases. The existing `evals/lint` case stays as the CI gate; the matrix is not in the CI matrix because 25 cases times 5 repeats would spend the eval budget on every pull request.

## Why

The old lint eval had one fixture, three planted violations, one model and regex grading with no clean control, so a model that always said YES passed and precision and variance were unmeasurable. The matrix makes both measurable, and a unit test shows an always-YES model scores a false-alarm rate of 1.0 on the clean control.

## Tradeoffs considered

- **One fixture with all 24 violations**: cheap, but violations interact and recall per check is confounded by the others. Rejected.
- **Free-text grading by a judge model**: richer, but adds a second noisy model. A numeric answer line keeps grading mechanical.
- **Limits**: judgment mutations are clear-cut instances, so their recall is an upper bound; each check has one mutation, so per-check recall over repeats measures run-to-run noise, not coverage of violation variants; the base project's cleanliness for judgment checks is a human judgment, only the structural checks are verified by code.
